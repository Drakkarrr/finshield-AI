## 0. Rules for the implementing agent (read first)

These extend [MASTER-PROMPT.md](./MASTER-PROMPT.md) §3 (rules R1–R11), which still apply.

1. **One implementation only.** Build on the code in `main`. Never re-implement something that exists
   (the P2–P4 duplication cost a full integration pass). If you think existing code is wrong, fix it
   in place and say so in the commit message.
2. **One branch per slice:** `qoder/S7.1-retention-safe-deletes`, and so on. One commit per slice. Open
   it for review; do not push to `main` and do not force-push without the user's explicit go-ahead.
3. **Never commit `.qoder/`** (it is git-ignored; keep it that way). Never commit `.env`, `*.db`,
   backups or secrets.
4. **Migrations:** the chain is `0001 → … → 0011`. The next one is `0012`, with a handwritten numeric
   revision id (not an autogenerated hash) and `down_revision` set to the current head. Run
   `alembic upgrade head && alembic downgrade base && alembic upgrade head && alembic check`.
5. **Tests or it didn't happen (R5).** For every slice, paste the real output of:
   - SQLite suite:
     `docker run --rm -v "$PWD/backend:/src" python:3.11-slim sh -c "cp -r /src /w && cd /w && pip install -q -r requirements.txt -r requirements-dev.txt && APP_ENV=test pytest -q"`
   - Postgres suite: the `postgres` job in `.github/workflows/ci.yml` (`TEST_DATABASE_URL`). Tests marked
     Postgres-only are skipped on SQLite, so RLS and audit-trigger changes need this run.
   - `mypy app scripts` and `ruff check app scripts tests`.
   - Frontend: `npm run lint` (ESLint and tsc) and `npm run build` in `platform-app/`.
   - The eval harness when screening logic changes: `python -m tests.eval.run_eval` with
     `RAG_EMBEDDER=hash` and, in the backend image, `minilm`. "No regression against baseline.json" is required.
6. **API contract.** If a route or schema changes, regenerate `backend/tests/openapi_snapshot.json` with
   the pinned dependencies (inside python:3.11, not a local Python 3.13), and diff it before
   committing. If `backend/app/permissions.py` changes, update `platform-app/src/lib/permissions.ts` in
   the same commit; the two MATRIX copies must stay identical.
7. **Determinism (R1) and reasons (R2).** No randomness in decision paths. Every new decision input
   adds a machine-readable `reason`. A failing dependency degrades to human review and never auto-approves.
8. **Honest docs (R7, R11).** Update `PROGRESS.md` (a new row per slice, with the commit, the test
   command and any deviations), the matching row in `docs/compliance/controls-matrix.md`, and the
   closed item in `limitations.md`. Relabel docs; never delete history.

## P7: Record-keeping integrity and truth

The fastest phase, and it fixes the P1 record-keeping failures. **Gate:** no screened record can
disappear without trace; every security-relevant event is audited; no doc or plan text claims a
feature that does not exist.

### S7.1 Retention-safe deletes (L1) · M · backend
- **Why:** `DELETE /api/v1/transactions/{id}` and `DELETE /api/v1/cases/{id}` hard-delete regulated records,
  with no retention check and no audit entry.
- **Do:**
  - Refuse (409, with the reason and `eligible_from`) any delete inside the retention window
    (`privacy.retention_years`) or of a record linked to a case or filing. Reuse the rules in
    `backend/app/domain/privacy.py`.
  - Outside the window, pseudonymise through the erasure path instead of deleting the row.
  - Audit every attempt, allowed or refused.
- **Files:** `backend/app/api/transactions.py`, `backend/app/api/cases.py`, `backend/app/domain/privacy.py`, a new test `backend/tests/test_retention_deletes.py`.
- **Accept:** tests show that a delete inside the window gives 409 and the row still exists; that a delete of a linked record gives 409; that an eligible record is pseudonymised and not removed; and that each attempt writes an audit entry.

### S7.2 Audit coverage (L9) · M · backend · parallel-safe with S7.3
- **Do:**
  - Audit failed logins (actor = pseudonymised email), API key create and revoke, user role changes, settings and flag changes (already done; verify), and data exports (audit export, transaction export, DSAR export).
  - Fill `audit_logs.ip_address` from the client IP behind a trusted proxy (honour `FORWARDED_ALLOW_IPS`), stored pseudonymised.
- **Files:** `backend/app/api/auth.py`, `keys.py`, `admin.py`, `audit.py`, `transactions.py` (export), `backend/app/domain/audit/`.
- **Accept:** one test per event type asserts the audit row; the audit chain still verifies; no raw email or IP appears in `audit_logs` (assert pseudonyms only).

### S7.3 Filing controls (L12) · S · backend + frontend
- **Do:**
  - Filing reads need `investigator` or above (MATRIX).
  - A `submitted` filing's narrative is locked; changes create a new audited version (`filing_versions` table, migration `0012`).
  - The UI shows the versions and states that FinShield does not e-file.
- **Files:** `permissions.py` + `permissions.ts`, `api/filings.py`, `db_models.py`, migration, `platform-app/src/app/filings/page.tsx`.
- **Accept:** RBAC matrix test (analyst → 403 on filing GET); PATCH on a submitted narrative → 409 unless it creates a version; the version history is returned and audited.

### S7.4 Four-eyes for detection changes (L4, technical part) · M · backend + frontend
- **Do:**
  - Model promotion and rule disable/override become a *proposal* that a **different** supervisor or admin must approve (`change_requests` table, migration).
  - RULE-001 (sanctions) cannot be disabled at all.
  - The approver, the proposer and both timestamps are audited.
- **Files:** `api/models.py`, `api/rules.py`, `config_service.py`, `domain/models_registry/`, migration, the Operations and Rules pages.
- **Accept:** tests show that self-approval is refused; that disabling RULE-001 → 422; that a proposal has no effect until approved; and that an approved change takes effect and is audited.

### S7.5 Production fail-safes (L2, L15 parts) · S · backend + compose
- **Do:**
  - With `APP_ENV=production`, refuse to start if `PAYMENTS_MODE=simulated` unless `ALLOW_SIMULATED_PAYMENTS=true` is set explicitly (local compose sets it).
  - `LISTS_DEMO_FIXTURES` defaults to `false` outside development.
  - A **stale** sanctions list (older than the `lists.max_age_hours` setting) degrades decisions: `in_review`, `degraded=true`, reason `list_stale`. Today only a *missing* list does.
  - Fix the readiness docstring in `api/health.py`.
- **Accept:**
  - Startup tests for both flags.
  - A stale-list test: the decision is `in_review` with the reason.
  - The eval shows no regression.

### S7.6 Truth cleanup (L16, small deviations) · S · docs + small code
- Remove or relabel the Enterprise plan claims ("SSO", "On-premise / VPC", "99.9% uptime SLA") in `config_service.py` until P8/P12 deliver them.
- DEPLOYMENT.md:
  - bring Phases 7, 8, 10 and 11 in line with S4.5 and S6.2, or mark them superseded;
  - remove Neon/PayMongo as current guidance.
- Fix the `permissions.py` docstring (it names a test file that doesn't exist).
- One password policy: minimum 12 characters at signup **and** on change (today it is 8 and 6).
- Remove the stale "open items" in PROGRESS.md (npm audit and stack ownership are resolved).
- Update Wiki §21 statuses to match P1–P6.
- **Accept:** a grep shows no "SSO", "99.9%" or "On-premise" in the plan definitions; the password policy is tested on both endpoints; the docs review is recorded in PROGRESS.md.

## P8: Identity and access

**Gate:** privileged users need MFA; logout and password changes revoke sessions; every failed login
counts toward a lockout and is audited; enterprise tenants can sign in with SSO; API keys are scoped
and expire.

### S8.1 Session revocation and lockout (L3) · M · backend + frontend
- **Do:**
  - Add `users.token_version`, included in the JWT as `tv`; `get_current_user` rejects a mismatch.
  - Logout (all sessions), password change and admin deactivation bump the version.
  - After 5 failed logins in 15 minutes, lock the account for 15 minutes; the counter is kept in Redis. Audited (S7.2).
  - Add a "Sign out everywhere" button in Settings.
- **Accept:** an old token gets 401 after a password change; the lockout test passes; the frontend handles the 401 by redirecting to login.

### S8.2 MFA: TOTP plus recovery codes (L3) · M · backend + frontend · depends on S8.1
- **Do:**
  - TOTP enrolment (QR code and secret shown once; the secret is encrypted with `crypto.py`) and 10 single-use recovery codes, stored hashed.
  - Login becomes two-step when MFA is on. Supervisor and admin are **required** to enrol on next login, enforced by a per-tenant setting.
  - Audit enrol, disable and recovery-code use.
- **Accept:** a test with `pyotp` drives the full login; a privileged user without MFA is blocked from privileged routes until enrolled; recovery codes are single-use.
- **Decision:** WebAuthn/passkeys now or later? The recommended default is TOTP now and WebAuthn in a later slice.

### S8.3 SSO via OIDC per tenant (L3) · L · backend + frontend · depends on S8.1
- **Do:**
  - Per-tenant OIDC config (issuer, client id, encrypted secret, allowed domains), using authorization-code flow with PKCE.
  - Just-in-time user provisioning with a default role; a role-mapping claim is optional.
  - Admin UI to configure it, and an "SSO only" switch that disables passwords for the tenant.
  - SAML is a later slice and only if a customer asks.
- **Accept:** an integration test against a containerised IdP (Keycloak dev image) signs in and provisions; "SSO only" refuses a password login.
- **Decision:** which IdP to test against; Keycloak is the recommended local stand-in.

### S8.4 API key scopes, expiry and rotation (L20) · M · backend + frontend
- **Do:**
  - Scopes: `screen`, `read`, `cases:write`, `admin`. A key may never exceed its creator's role.
  - An optional expiry; a rotation endpoint returns a new key and keeps a grace period on the old one.
  - Use the `key_digest` lookup (migration 0011).
- **Accept:** a test per scope (403 outside the scope), an expired key gives 401, rotation works with a grace window, and the SDK (`sdk/python`) documents scopes.

## P9: Detection quality and list coverage

**Gate:** every sanctions list the target jurisdictions require is imported from its official source,
with provenance on every hit; PEP data comes from a real (licensed) source in production; the risk
model is validated on labelled outcomes, with a signed model card.

### S9.1 More official sanctions lists (L2) · L · backend
- **Do:**
  - Importers for UN Security Council Consolidated (XML), EU Financial Sanctions Files (XML), UK OFSI Consolidated (CSV/XML), and the Philippines AMLC designations if a machine-readable source exists (check before building).
  - Each importer is a `ListProvider` source, with version, checksum, effective dates and provenance on every hit.
  - Per-tenant choice of active lists (setting `lists.sources`).
  - Daily refresh through the existing `finshield.lists.refresh` task.
- **Files:** `backend/app/domain/lists/importers.py`, `backend/scripts/import_lists.py`, `worker/tasks.py`, fixtures for tests.
- **Accept:**
  - Parser tests on small committed fixtures from each official format.
  - A real import of each list in the backend image (paste the entry counts).
  - Eval scenarios for at least one hit per list.
  - Hits show `source` and `list_version`.

### S9.2 PEP feed adapter (L2) · M · backend
- **Do:** a provider interface for a licensed PEP/adverse-media vendor (REST, with a cached snapshot); it is a contract-tested stub until a vendor is chosen. Remove the fictional fixture from every non-development path.
- **Decision (blocking):** which PEP vendor (for example Dow Jones, LSEG World-Check, ComplyAdvantage, Sanction Scanner). The key and contract come from the user.
- **Accept:** contract tests run against a recorded response; production refuses to start with fixture PEP data.

### S9.3 Non-Latin name matching (L17) · M · backend
- **Do:** transliterate Cyrillic, Arabic, Greek and CJK (romanised) before normalising, using a deterministic library pinned by version (for example `anyascii` or `unidecode`), and match on both the original and the transliterated form.
- **Accept:** new eval scenarios (Cyrillic and Arabic names that appear on OFAC/UN lists) produce hits; existing metrics show no regression; the measured matching cost is recorded (S6.5 numbers).

### S9.4 Model validation and governance (L4) · L · backend + docs
- **Do:**
  - Build a labelled dataset from resolved cases (`confirmed_suspicious` / `false_positive`), anonymised, as an export script.
  - Fit or calibrate the `RiskModel` weights (still classical, ruling D1) on it, with a held-out validation report: precision, recall and AUC per segment.
  - Register it as v2 in **shadow mode**, compare it with v1 for N weeks, then promote through S7.4 four-eyes.
  - The model card is filled in with intended use, data, metrics, limitations and the approver.
- **Depends on:** S7.4, plus enough resolved cases (synthetic data is not acceptable for validation).
- **Accept:** the validation report is committed under `docs/compliance/model-validation/`; the eval baseline is updated with v2; the promotion is approved by a second person in the audit log.

### S9.5 Server-side pagination for cases and filings (S5.4 deviation) · S · backend + frontend
- **Do:** `limit`/`offset` plus `X-Total-Count` on `GET /api/v1/cases` and `/api/v1/filings`; the UI pages on the server.
- **Accept:** a paging test like `test_transaction_list_reports_the_total_for_paging`; the snapshot is updated.

## P10: Keys, encryption and supply chain

**Gate:** keys live in a KMS and rotate; the audit chain is anchored outside the system; sensitive
narratives are encrypted at rest; images are pinned by digest and scanned, with SAST in CI.

### S10.1 KMS-backed keys and rotation (L6) · L · backend
- **Do:**
  - A `KeyProvider` interface in `crypto.py`: a local provider (today's HKDF from `DATA_ENCRYPTION_KEY`, for development) and a cloud KMS provider (envelope encryption with versioned data keys).
  - Every ciphertext and signature records its key version.
  - The audit signing key is held in the KMS (asymmetric signing), with old public keys published for verification.
  - A rotation runbook and command that re-encrypts columns in batches.
- **Decision (blocking):** which KMS: AWS KMS, GCP KMS, Azure Key Vault, or HashiCorp Vault Transit. It follows the PaaS choice in S12.4.
- **Accept:**
  - Rotation test: old data stays readable, new writes use the new version, and old exports still verify against the published old key.
  - The local provider keeps the tests green.

### S10.2 External anchoring of audit chain heads (L6) · M · backend + worker · depends on S10.1
- **Do:** a scheduled task publishes each tenant's chain head (seq and hash, signed) to an append-only store outside the database: an object-lock (WORM) bucket and/or an RFC 3161 timestamp authority, and optionally the tenant's webhook. `scripts/verify_audit_export.py` gains `--anchors` to check an export against them.
- **Accept:** a tamper test: rewrite the chain and re-sign it with the server key, and anchor verification still fails.

### S10.3 Encryption at rest for narratives and transport to the DB (L7) · M · backend + deploy
- **Do:**
  - Column-encrypt SAR/STR narratives, case notes and investigator comments (migration with a batched backfill), keeping search on non-sensitive fields only.
  - `sslmode=require` for managed Postgres.
  - Encrypt backups (`age` with a public recipient key, or SSE-KMS when `BACKUP_S3_URI` is set), plus the matching restore support.
  - The deployment guide requires encrypted storage.
- **Accept:** the database shows ciphertext for those columns (test); the restore drill passes with encrypted archives (paste the transcript); the eval shows no regression.

### S10.4 Supply chain and perimeter tests (L14) · M · CI + backend
- **Do:**
  - Pin the base images by digest.
  - Add a Trivy image scan and Semgrep/Bandit SAST, both blocking on high/critical.
  - Add header tests for the API and the web app (`test_security_headers.py`).
  - Move rate limits to Redis (slowapi storage URI) and test them under `APP_ENV=test` with a flag that enables them.
- **Accept:** CI shows the new jobs passing; the header and rate-limit tests pass; limits are shared across 2 uvicorn workers (test).

## P11: Operations, scale, DR and billing

**Gate:**
- critical alerts reach a human;
- p95 holds at 10× concurrency with horizontal scale;
- there is a measured RTO/RPO with a recurring automated restore drill;
- billing is complete in Stripe test mode;
- retention purges run under review.

### S11.1 Monitoring stack and paging (L5, technical) · M · deploy
- **Do:**
  - Compose profile `monitoring`: Prometheus (scraping `/metrics` with `METRICS_TOKEN`), Alertmanager (with the existing `deploy/prometheus/alerts.yml`), Grafana with a FinShield dashboard (pipeline latency per stage, decisions, degraded, queue depth, list age, SLA).
  - Route critical alerts to a pager or email.
- **Accept:** `promtool check rules` passes; a forced breaker-open fires `CircuitBreakerOpen` to the receiver (screenshot or log); the dashboard JSON is committed.

### S11.2 Horizontal scale and nightly load gate (S6.5) · M · deploy + CI · depends on S10.4
- **Do:**
  - Run N backend replicas behind the TLS proxy (Caddy `reverse_proxy` with several upstreams) and set `uvicorn --workers` from `WEB_CONCURRENCY`.
  - Add a nightly k6 job (`loadtest/screening.js`) against an ephemeral stack, with the thresholds as a regression gate.
- **Accept:** a documented run in which p95 at 50 clients is under 2 s with the stated replicas and CPUs (update `docs/operations/performance.md`), and the nightly job is green.

### S11.3 DR targets, PITR and an automated restore drill (L8) · M · deploy + CI
- **Do:**
  - Set targets (proposal: RPO 15 min with PITR, RTO 2 h), enable PITR on managed Postgres, and run a weekly CI job that restores the latest archive into a clean Postgres, runs `audit_check`, and records the duration.
  - Document failover.
- **Accept:** the CI job is green and its duration is recorded; DEPLOYMENT.md Phase 9 carries the targets and the latest drill result.

### S11.4 Billing completion (L15) · L · backend + frontend
- **Do:**
  - Stripe Billing subscriptions (plans as Stripe Prices), proration on upgrade, dunning (`invoice.payment_failed` → grace → downgrade), refunds (credits clawed back, audited), invoices and the customer portal link.
  - Webhooks for `customer.subscription.*` and `invoice.*`, idempotent and signature-verified (same pattern as `domain/payments.py`).
- **Decision (blocking):** the user provides Stripe **test-mode** keys and a webhook secret (never committed).
- **Accept:** a test-mode run with the Stripe CLI (`stripe trigger …`) for each event, with the transcript pasted; unit tests per event; still no card data in the DB.

### S11.5 Retention purge and an erasure ledger (L13) · M · backend + worker
- **Do:**
  - A reviewed purge job: it lists records past retention, needs an admin approval (S7.4 four-eyes), then pseudonymises.
  - An erasure ledger outside the database (WORM bucket, same as S10.2), so erasures can be re-applied after a restore.
  - Per-tenant or per-jurisdiction retention years.
- **Accept:** a test shows records are purged only after approval; the restore drill re-applies erasures from the ledger (transcript).

## P12: Assurance and go-live

Largely process and external work; the agent prepares artefacts, people sign them off. **Gate:** a
production deployment on the chosen PaaS with TLS A+, the critical policies in place, a pen test done
and its findings fixed, and change control enforced.

### S12.1 Security policies and incident response (L5 process, L10) · M · docs
- **Do:**
  - Write a minimal policy set under `docs/compliance/policies/`: information security, access control, change management, incident response, breach notification (GDPR Art. 33: 72 h; PH NPC rules), vendor management, and data retention (link `retention.md`).
  - Run a tabletop exercise (scenario: audit chain break) and record it.
- **Accept:** the documents are reviewed and owned by named people (the user); the tabletop record is committed; questionnaire answers update from No to Partial or Yes with evidence.

### S12.2 Change control (L11) · S · repo settings + docs
- **Do:**
  - Branch protection on `main`: required reviews and required CI checks, no force-push.
  - Tagged releases (`v2.5.0`…) with a CHANGELOG generated from the slice ledger.
  - A CODEOWNERS file.
- **Decision:** the user enables branch protection; agents cannot.
- **Accept:** a screenshot or export of the protection rules; the first tagged release.

### S12.3 Pen test and SOC 2 readiness (L10) · external
- **Do:** commission an external pen test of the staging deployment (web, API, auth); fix every high and critical finding as its own slice; run a SOC 2 readiness gap assessment against `controls-matrix.md`.
- **Decision (blocking):** vendor and budget.
- **Accept:** the report is stored privately (not in the repo); the remediation slices are ledgered; the questionnaire is updated.

### S12.4 Managed PaaS deployment, staging then production (D9, S6.2) · L · deploy
- **Do:**
  - Deploy the backend, worker, beat and frontend, with managed Postgres (pgvector, PITR, encryption at rest) and managed Redis, on the chosen PaaS.
  - Use the platform secret store for every secret.
  - Use a custom domain with TLS; `COOKIE_SECURE=true`, `HSTS_ENABLED=true`, a correct `FORWARDED_ALLOW_IPS`, and `CORS_ORIGINS` set to the real origin.
  - Staging first, with the e2e checks (`register → screen → webhook → audit verify`) and the axe scan run against it.
- **Decision (blocking):** which PaaS: Railway, Render, Fly.io, or a cloud provider's managed containers. It also decides the KMS (S10.1).
- **Accept:** SSL Labs grade A or better (screenshot), the securityheaders.com report, e2e 23/23 and axe 0 serious on staging, then production.

### S12.5 Kubernetes / Helm (S6.7) · L · conditional
- Only if a customer or procurement requires self-hosting. Write a Helm chart with an HPA, and run the S11.2 load profile on a clean cluster.
